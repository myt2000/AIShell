# AIShell 自动日志解析方案

## 1. 文档目的

本文定义 AIShell 中“消息推送日志自动解析”的完整流程。

目标是：用户在 AI 对话中输入查询需求后，AIShell 能够自动完成：

1. 识别查询业务和必要参数；
2. 根据 `task_id`、`cid`、业务类型选择起始模块；
3. 自动打开对应的 SSH 服务器窗口；
4. 在 SSH 终端执行只读 Linux 查询命令；
5. 捕获命令输出并返回 AI 对话窗口；
6. 根据本地规则解析结果，决定下一步模块；
7. 循环查询，直到流程结束；
8. 在对话中输出过程、原始日志、判断结果和最终结论。

当前版本已经具备：

- AI 对话；
- AI 生成 `open_group`、`open_profile`、`run` 动作；
- SSH 窗口打开；
- 只读命令检查；
- 命令发送和终端输出抓取；
- 命令执行后的 AI 自动回传分析。

当前尚未完成的是“规则驱动的全流程自动查询”。目前 AI 生成命令后，仍主要依赖用户点击执行，且下一模块的跳转和结果归因还没有完全交给本地流程引擎。

## 2. 用户使用方式

### 2.1 单业务查询

用户输入：

```text
查询 task_id=RASS_1230_xxx，cid=cid_xxx 的消息下发情况
```

AI 应识别出：

- 查询类型：消息下发链路；
- 起始模块：`psc`；
- 必要参数：`task_id`、`cid`；
- 查询模式：自动模式或逐步确认模式。

### 2.2 多业务查询

用户点击 AI 窗口中的“加号”，可以增加多个相互独立的业务查询：

```text
业务 1：task_id=RASS_xxx，cid=cid_xxx
业务 2：task_id=OSS_yyy，cid=cid_yyy
```

每个业务必须拥有独立的查询上下文：

- 不混用 `task_id`；
- 不混用 `cid`；
- 不混用 SSH 服务器；
- 不混用命令输出；
- 不覆盖前一个业务的中间结论。

最终结果按业务分别展示。

## 3. 自动模式和确认模式

### 3.1 自动模式

自动模式下，用户确认一次“开始查询”后：

```text
识别参数 → 打开 SSH → 执行命令 → 回传输出 → 本地解析 → 跳转下一模块 → … → 输出结论
```

自动模式仍然必须满足：

- 所有命令均为只读命令；
- 每条命令执行前经过本地安全校验；
- 不允许 AI 自行执行写入、删除、重启等操作；
- SSH 连接失败、命令超时、结果不明确时暂停并提示用户。

### 3.2 逐步确认模式

逐步确认模式下，每到一个新模块都展示：

- 将连接的服务器；
- 将执行的命令；
- 命令用途；
- 上一步日志判断；
- 用户确认/跳过按钮。

默认建议：首次上线使用逐步确认模式，验证稳定后再开放自动模式。

## 4. 查询参数

### 4.1 必要参数

| 参数 | 说明 |
|---|---|
| `task_id` | 推送任务 ID |
| `cid` | 设备 CID |

### 4.2 可选参数

| 参数 | 说明 |
|---|---|
| `appid` | 应用 ID，用于补充过滤 |
| `date` | 日志日期，格式 `YYYYMMDD` |
| `vendor` | 厂商，如华为、小米、OPPO、vivo、魅族、iOS |
| `time_start` | 起始时间 |
| `time_end` | 结束时间 |
| `phone` | 手机号，只有在已配置手机号到 CID 的查询规则时使用 |

### 4.3 参数不足时的行为

如果没有 `task_id`，AI 不得猜测示例值，应提示：

```text
请提供 task_id。最好同时提供 cid。
如果没有 task_id，请提供 appid、cid、推送时间或手机号。
```

最多一次询问两个缺失参数，避免连续询问影响使用体验。

## 6. 命令生成规范

### 6.1 原则

AI 只负责选择查询意图和填写参数，不能自由编写字段解析命令。

命令由本地模板生成，优先查询原始日志，再由本地规则引擎解析字段。

### 6.2 基础模板

按 `task_id + cid` 查询：

```bash
zgrep -H -F -- "${task_id}" \
  "${module_path}/${log_type}-${date}-"* \
  | grep -F -- "${cid}"
```

只按 `task_id` 查询：

```bash
zgrep -H -F -- "${task_id}" \
  "${module_path}/${log_type}-${date}-"*
```

查询指定时间段：

```bash
find "${module_path}" -type f \
  -name "${log_type}-*" \
  -newermt "${time_start}" ! -newermt "${time_end}" \
  -print0 | xargs -0 zgrep -H -F -- "${task_id}" \
  | grep -F -- "${cid}"
```

### 6.3 参数校验

执行前必须校验：

```text
task_id: 只允许字母、数字、下划线、中划线
cid:      只允许字母、数字、下划线、中划线
date:     只允许 YYYYMMDD
module:   只能来自本地模块白名单
log_type: 只能来自本地日志类型白名单
```

禁止把未经校验的用户输入直接拼接到 shell 命令中。

### 6.4 只读限制

禁止命令包括但不限于：

```text
>
>>
tee
touch
mkdir
rm
mv
cp
chmod
chown
kill
pkill
reboot
shutdown
halt
dd
mkfs
vi
vim
nano
sed -i
find -delete
```

同时禁止通过 `sh -c`、`bash -c`、`xargs` 嵌套执行未审核命令。

## 7. 日志字段解析规则

### 7.1 初始模块 `rp-bi`

字段位置从 1 开始：

| 字段 | 含义 |
|---:|---|
| 1 | 时间 |
| 2 | msgId |
| 3 | cid |
| 4 | 下发类型 |
| 7 | taskId |
| 8 | appId |
| 10 | 下一模块 |

第 4 个字段：

| 值 | 含义 | 处理 |
|---:|---|---|
| `0` | 离线下发 | 根据第 10 字段进入 `sdp` 或 `omp` |
| `1` | 在线下发 | 进入 `im → cm → as` |
| `6` | 用户黑名单 | 打印全部初始日志，结束 |
| `9` | 无效 CID | 打印全部初始日志，结束 |
| 其他 | 异常状态 | 打印全部初始日志，结束 |

第 10 个字段：

| 值 | 含义 |
|---|---|
| `SDP` | 进入厂商条件过滤流程 |
| `OMP` | 进入离线库流程 |
| `0` | 进入在线 `im` 流程 |

### 7.2 在线流程日志

```text
初始模块 rp-bi
  → im/rp-message
  → cm/rp-message
  → as/rp-message
```

`im` 可能出现多条记录。多条记录通常表示在线重试或假在线，不能只取第一条。

`as/rp-message` 的常用 actionId：

| actionId | 含义 |
|---:|---|
| `0` | 个推到达 |
| `10000` | 通知展示 |
| `10010` | 通知点击 |
| `10030` | 透传到达或通知启动应用 |
| `10009` | iOS 展示 |
| `10019` | iOS 点击 |

### 7.3 SDP 流程

```text
初始模块 rp-bi
  → sdp/rp-command
  → 对应厂商模块
  → gtpr/rp-bi 或厂商 push-result
```

`sdp/rp-command` 第 2 个字段包含 `SUCCESS` 时，认为厂商下发请求成功；不包含 `SUCCESS` 时，打印 `sdp/rp-command` 全部结果并结束。

成功值映射：

| 结果 | 厂商模块 |
|---|---|
| `GTPS_HW_SUCCESS` | `gtps-hw` |
| `GTPS_XM_SUCCESS` | `gtps-xm` |
| `GTPS_VV_SUCCESS` | `gtps-vv` |
| `GTPS_OP_SUCCESS` | `gtps-op` |
| `GTPS_MZ_SUCCESS` | `gtps-mz` |
| `HPS_HOSHW_SUCCESS` | `hps-hoshw` |
| `IOS_SUCCESS` | `apn`、`apns` |

安卓厂商模块处理：

1. 先查厂商模块 `rp-bi`；
2. 如果存在匹配记录，再查 `gtpr/rp-bi`；
3. 如果没有匹配的 `rp-bi`，改查厂商模块 `push-result`；
4. 输出厂商 token、厂商 messageid、个推 code 和错误原因。

`push-result` 中 `200` 只表示个推向厂商请求成功，不代表用户一定收到消息。

### 7.4 iOS 流程

```text
初始模块 rp-bi
  → sdp/rp-command
  → apn/apns rp-bi
  → gpmrs 展示回执
  → as 在线补发查询
```

`apn/apns rp-bi` 第 2 个字段：

| 值 | 含义 |
|---|---|
| `ok` | APNs 下发成功，继续查 `gpmrs` 和 `as` |
| 其他 | iOS 厂商侧处理失败，打印完整日志并结束 |

### 7.5 OMP 流程

```text
初始模块 rp-bi
  → omp/rp-bi
```

判断 `omp/rp-bi`：

- 只有一条记录，且第 5 个字段为 `1`：打印全部 OMP 日志并结束；
- 有多条记录，且存在第 5 个字段为 `0`：打印全部 OMP 日志，继续 `im → cm → as` 查询在线补发；
- 结果不符合以上情况：标记为“需要人工判断”，不自动猜测。

## 8. SSH 自动执行协议

### 8.1 查询任务状态

每个业务维护一个独立状态对象：

```typescript
interface LogQueryTask {
    id: string
    taskId: string
    cid: string
    appId?: string
    date?: string
    currentModule: string
    currentLogType: string
    status: 'waiting' | 'opening' | 'running' | 'parsing' | 'finished' | 'paused' | 'failed'
    steps: LogQueryStep[]
    rawOutputs: LogQueryOutput[]
    conclusions: string[]
}
```

### 8.2 单步执行状态机

```text
WAITING_PARAMS
  → RESOLVE_ENTRY_MODULE
  → OPEN_SSH
  → WAIT_SESSION_READY
  → BUILD_COMMAND
  → SAFETY_CHECK
  → SEND_COMMAND
  → WAIT_OUTPUT
  → PARSE_RESULT
  → DECIDE_NEXT_STEP
  → OPEN_NEXT_SSH / SEND_NEXT_COMMAND
  → FINISHED
```

### 8.3 AI 与本地执行器的职责

AI 负责：

- 理解自然语言；
- 提取 `task_id`、`cid`、时间等参数；
- 解释规则引擎给出的结果；
- 向用户说明当前进度和最终结论。

本地执行器负责：

- 选择模块和日志类型；
- 生成固定命令；
- 打开/复用 SSH 窗口；
- 等待会话连接完成；
- 发送命令并捕获输出；
- 按字段规则判断下一步；
- 记录每一步原始输出。

不要让 AI 直接决定任意 shell 命令或任意下一模块。

### 8.4 建议的动作协议

在现有 `open_group`、`open_profile`、`run` 之外，增加一个业务查询动作：

```json
{
  "type": "log_query",
  "query_id": "query_xxx",
  "task_id": "RASS_xxx",
  "cid": "cid_xxx",
  "mode": "auto"
}
```

前端收到后，不再让 AI 逐条拼接动作，而是交给 `LogQueryOrchestrator` 执行完整流程。

执行器向 AI 回传结构化事件：

```json
{
  "type": "log_query_event",
  "query_id": "query_xxx",
  "step": "parse_result",
  "module": "spd",
  "log_type": "rp-bi",
  "raw_output": "...",
  "interpretation": {
    "delivery_type": "online",
    "next_module": "im"
  },
  "next": "im"
}
```

### 8.5 SSH 窗口复用原则

打开服务器时按以下顺序处理：

1. 优先复用已经打开且连接成功的目标服务器；
2. 没有可复用窗口时，通过 profile 打开 SSH；
3. 等待 `session.open === true` 后再发命令；
4. 命令只发送到当前查询任务绑定的 SSH 标签页；
5. 查询结束后默认保留窗口，方便用户查看原始日志；
6. 不自动关闭用户原本已打开的窗口。

## 9. 输出回传和结果展示

每一步都要保存三类信息：

1. 执行命令；
2. 原始输出；
3. 规则解析结果。

对话中建议展示：

```text
业务：RASS_xxx / cid_xxx

步骤 1/4：psc/rp-bi
结果：第 4 个字段为 1，判断为在线下发

步骤 2/4：im/rp-message
结果：发现 2 条记录，可能存在在线重试或假在线

步骤 3/4：cm/rp-message
结果：已找到对应 cm 实例

步骤 4/4：as/rp-message
结论：发现 actionId=0，表示个推到达
```

原始日志建议折叠展示，默认展示规则解释，用户点击后再展开完整输出。

## 10. 异常和超时处理

### 10.1 SSH 连接失败

暂停当前业务，提示：

```text
无法连接服务器：${server}
当前步骤：${module}/${log_type}
请选择：重试、切换服务器、跳过本步骤、结束查询。
```

### 10.2 命令超时

建议默认超时 30 秒。超时后：

- 不重复执行可能产生大量输出的命令；
- 保留已收到的部分输出；
- 提示用户是否扩大时间范围或改用更窄条件查询。

### 10.3 没有日志结果

不能直接判定“没有推送”或“推送失败”，应区分：

- 日期可能不正确；
- 日志文件模式可能不匹配；
- 查询服务器不正确；
- 日志已归档；
- task_id/cid 不完整。

### 10.4 规则无法判断

统一标记：

```text
日志已查到，但当前规则无法判断下一步，已暂停自动流程，请人工确认。
```

## 11. 安全要求

- AI 只读账号不能执行任何写入或变更命令；
- 所有命令必须通过本地白名单和参数校验；
- 禁止把密码、私钥、token 写入 AI 上下文；
- 原始日志回传 AI 前应限制大小并做智能截断；
- 多业务查询必须隔离日志和上下文；
- 自动模式不能绕过用户一次性启动确认；
- 任何异常结果不得由 AI 编造结论。

---

## 12. 建议实现拆分

### 第一阶段：规则库

新增本地规则文件，至少包含：

- 模块路径；
- 起始模块识别；
- 日志类型和文件模式；
- 字段位置；
- 状态码解释；
- 下一模块路由；
- 固定命令模板。

### 第二阶段：流程执行器

新增 `LogQueryOrchestrator`：

- 创建查询任务；
- 打开或复用 SSH；
- 执行模板命令；
- 获取终端输出；
- 调用规则解析器；
- 生成下一步任务。

### 第三阶段：AI 对话接入

- AI 只生成 `log_query` 动作；
- 执行器通过事件回传进度；
- AI 将事件转换为用户可读说明；
- 完成后保存查询历史。

### 第四阶段：多业务和自动模式

- 支持加号创建多个 `query_id`；
- 支持并行或串行执行策略；
- 增加自动/确认模式开关；
- 增加暂停、重试、跳过、终止按钮。

## 13. 完整示例

用户输入：

```text
帮我自动查询 task_id=RASS_1230_xxx，cid=cid_xxx 的消息有没有下发成功
```

系统流程：

```text
1. 识别 RASS → 起始模块 psc
2. 复用或打开 psc SSH 服务器
3. 执行 psc/rp-bi 固定查询命令
4. 解析第 4 个字段
5. 如果为 1 → 查询 im/rp-message
6. 根据 im 结果查询 cm/rp-message
7. 查询 as/rp-message
8. 解析 actionId
9. 将每一步结果回传 AI
10. 输出最终结论和完整查询链路
```

最终对话示例：

```text
查询完成。

任务：RASS_1230_xxx
设备：cid_xxx
链路：psc → im → cm → as

判断结果：
- 初始模块第 4 个字段为 1，属于在线下发；
- im 出现 2 条记录，存在在线重试迹象；
- cm 已收到下发请求；
- as 出现 actionId=0，表示个推到达。

结论：消息已到达个推客户端链路。若客户端仍未展示，继续检查客户端通知权限、消息类型和 SDK 回执。
```
